# 07 一次 SSH 连接背后的原理

这一篇用于回答“为什么这样设计”。不要求你计算密码学公式，也不需要记住每个算法名称。先完成前面的实际登录，再回来读会更容易。

## 用六步理解常见连接流程

下面是帮助建立概念的简化流程；实际协议包含协商、消息交互和可能的再次密钥交换。

```text
1 找地址并建立网络连接
          ↓
2 交换版本信息并协商算法
          ↓
3 密钥交换，服务端证明自己的主机身份
          ↓
4 双方启用协商出的加密与完整性保护
          ↓
5 客户端以密码、公钥等方式完成用户认证
          ↓
6 开启 Shell、执行命令、传文件或建立转发通道
```

### 1 网络连接必须先成立

域名需要解析到地址，路由和防火墙需要允许到达目标服务。常见 SSH 使用 TCP 连接。

因此超时可能发生在用户认证之前。换一把用户密钥不能修复错误地址或断开的网络。

### 2 双方需要协商都支持的方式

两端会交换协议版本信息，并协商密钥交换、主机签名、加密和完整性保护等算法。旧服务器和新客户端可能因为缺少共同支持的算法而失败。

“客户端不支持某算法”和“你的账号密码错了”发生在不同阶段。排错时先找阶段，不能把所有失败归为密码问题。

### 3 服务端证明自己的身份

服务端用主机私钥对密钥交换相关数据签名，客户端验证签名，并按本机策略检查主机公钥是否可信。

第一次连接需要通过可信渠道确认主机指纹。之后客户端可以用保存的记录发现身份变化。只有加密而没有正确识别对方，不能保证你连到的是原本想连接的对象。

### 4 建立会话加密材料

密钥交换让双方得到用于通信的共享秘密，再派生会话所需的密钥。典型现代方案并不是把用户登录私钥发送过去，也不是直接用用户公钥加密整场终端会话。

大量数据一般使用对称加密处理，并结合协议协商出的完整性保护机制。公钥密码技术承担密钥交换相关认证和用户认证等角色；不同算法的具体机制不同。

### 5 验证你是否能登录这个账号

通道建立后，服务端还要验证客户端的用户身份。

- 密码认证：客户端通过受保护的连接提供相应认证信息。
- 公钥认证：客户端用用户私钥签名，服务端验证，并检查目标账号是否允许使用这个公钥。

公钥算法、授权列表、账号策略、文件权限和其他认证要求都可能影响结果。真实系统还可能要求多种认证方式组合。

### 6 开启你实际要用的功能

用户认证通过后，SSH 连接可以承载不同通道，例如交互式终端、单条命令、SFTP 或端口转发。功能是否允许仍受服务端策略控制。

所以“能登录”不一定意味着“允许所有端口转发”，也不意味着账号有权限读取全部文件。

## 把常见文件放回流程里

| 文件或材料 | 对应的作用 |
| --- | --- |
| 服务端主机私钥 | 服务端证明自己持有对应的主机密钥 |
| 客户端 `known_hosts` | 客户端记录和检查主机身份 |
| 客户端用户私钥 | 用户公钥认证时签名 |
| 服务端 `authorized_keys` | 授权哪些用户公钥可以登录指定账号 |
| 客户端 `config` | 告诉客户端连接地址、账号和选项 |
| 协商派生的会话密钥 | 为连接中的通信提供加密等保护 |

用户公钥和主机公钥都可能使用 Ed25519 等算法。算法相同不代表用途相同。

## SSH 加密保护哪一段

在端口转发中，SSH 加密保护客户端到 SSH 服务端之间的传输。SSH 服务端再向最终目标发起的那一段连接，是否加密取决于目标协议，例如 HTTPS 或明文 HTTP。

```text
客户端 ═══ SSH 加密连接 ═══ SSH 服务端 ─── 最终目标
                                         ↑
                              这一段不能自动视为 SSH 加密
```

加密也不能让已经被入侵的客户端或服务端变得可信。端点上的程序仍可能读取它有权限接触的数据。

## 为什么不能只看“免密”两个字

“免密”是口语，可能指不再输入服务端密码、代理记住了私钥，或其他自动化机制。它没有说明认证是否存在、私钥是否有口令、主机身份是否已确认。

更准确地描述你的状态是：“使用公钥认证，私钥有口令，当前由本机代理提供签名。”

## 自测

1. SSH 整场通信都是用你的用户公钥直接加密的吗？
2. 用户公钥已授权，是否意味着可以忽略目标主机指纹？
3. 隧道出口继续连接明文 HTTP，是否能认为全程都由 SSH 加密？

答案：1. 不是，会协商并派生会话密钥。2. 不能，两者检查的是不同身份。3. 不能，要分别看各段连接。

## 参考资料

- [RFC 4253 SSH 传输层](https://www.rfc-editor.org/rfc/rfc4253)：版本交换、协商、密钥交换与保护。

- [RFC 4254 SSH 连接协议](https://www.rfc-editor.org/rfc/rfc4254)：会话和转发通道。

这些 RFC 用于解释协议结构，其中的历史算法列表不等于当前安全配置建议。实际算法支持以你使用的 OpenSSH 版本及本机手册为准。
