# 08 排错与命令速查

遇到失败时先看报错属于哪个阶段，再做最小范围的检查。前面的 `ssh-lab` 是你在[第四篇](04-config-and-files.md)建立的客户端别名，未建立前不要直接照抄使用。

## 先按这条顺序判断

```text
本机找不到命令？ → 检查客户端
       ↓
地址无法解析？   → 检查地址或 DNS
       ↓
连不到端口？     → 检查开机、服务、路由和防火墙
       ↓
主机身份不一致？ → 独立核对目标身份
       ↓
认证不通过？     → 检查账号、密码、公钥和权限
       ↓
登录后功能失败？ → 检查目标程序、路径和服务端策略
```

## 按报错查问题

| 提示或现象 | 通常发生在哪 | 优先检查 |
| --- | --- | --- |
| `command not found: ssh` / 无法识别 `ssh` | 客户端 | 是否安装客户端，命令路径是否正常 |
| `Could not resolve hostname` | 地址解析 | 地址拼写、别名配置、DNS；是否忘记把示例替换 |
| `Connection timed out` | 网络连接 | 目标是否开机、地址是否可达、端口及防火墙；不是先改密码 |
| `Connection refused` | 连接目标端口 | 该地址和端口是否运行 SSH 服务；也可能是网络设备主动拒绝 |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 主机身份检查 | 地址是否变化、是否重装或更换密钥；先核对指纹 |
| `Permission denied` | 用户认证 | 目标账号是否正确、是否允许登录、认证材料是否匹配 |
| `Permission denied (publickey)` | 用户公钥认证 | 是否提供正确私钥，目标是否授权对应公钥，权限和策略是否符合要求 |
| `Too many authentication failures` | 用户认证 | 客户端或代理是否尝试过多身份；指定对应密钥并限制身份 |
| `UNPROTECTED PRIVATE KEY FILE` | 本地私钥权限 | 私钥是否允许其他用户读取；Mac/Linux 检查权限和归属 |
| `no matching ... found` | 算法协商 | 两端版本及策略是否兼容；优先了解升级路径，不随意开启旧算法 |
| 登录后文件操作 `Permission denied` | 目标文件权限 | 这时可能已登录成功，检查文件和目录权限，不要误判为认证失败 |
| B 的一侧地址能连，另一侧不能连 | 地址、监听、网络或策略 | 对照双网卡拓扑检查目标 IP、对应地址监听、两侧防火墙与返回路径 |
| 跳板出现 `administratively prohibited` | 转发策略 | 检查 B 是否允许到 C 的 TCP 转发，及账号、公钥和 Match 限制 |
| `Bad configuration option` | 读取配置 | 检查是否把服务端 ListenAddress 等选项写进了客户端 config，或有拼写/版本问题 |
| `no such identity` / 私钥文件找不到 | 客户端读取身份 | 检查 -i 或 IdentityFile 是否指向当前客户端上的真实文件；本教程填私钥路径，勿误填另一台设备的路径 |
| `Broken pipe` / `Connection reset` | 已建立连接中断 | 检查网络、休眠或服务端会话策略；重连后再判断原任务状态 |

“通常”不等于唯一原因。网络设备的过滤、系统策略和具体版本可能改变表现。

## 当前究竟在等我输入什么

| 提示或界面 | 应该怎么处理 |
| --- | --- |
| 主机指纹及 `yes/no` 询问 | 先核对目标主机身份，一致后再输入 yes |
| `alice@地址's password:` | 输入目标账号密码；不显示字符或星号通常正常 |
| `Enter passphrase for key ...` | 输入提示路径对应的本地私钥口令 |
| `[sudo] password for ...` 等 sudo 提示 | 按该系统策略输入执行 sudo 所要求的账号凭据；不等于 SSH 在重新登录 |
| `sftp>` | 正在 SFTP 命令环境，先用 bye 退出再运行普通 Shell 命令 |
| `ssh -N -L ...` 认证后没有提示符 | 隧道可能正常在前台运行，应按第五篇从浏览器测试 |

如果分不清自己在本机还是远程，先看 `hostname`、`whoami`，必要时用第二篇的 `printenv SSH_CONNECTION` 辅助判断。自连接两端主机名相同是正常的。

## 隧道窗口没反应或网页打不开

按[第五篇的同机实验](05-network-and-tunnels.md#选做-在一台-mac-上准备可访问的网页服务)分开检查：

1. 窗口一的 Python 服务是否仍运行，本机浏览器能否直接访问 `http://127.0.0.1:3000`。
2. 窗口二的 SSH 是否认证成功、是否还在运行；`-N` 不进入远程 Shell，窗口安静不等于卡死。
3. 浏览器是否访问**客户端这侧**的 `http://127.0.0.1:8080`；网页服务需支持你使用的 HTTP/HTTPS 协议。
4. 若出现 `Address already in use`，先确认报错来自 Python 的 3000 端口，还是 SSH 的本地 8080 端口。重复运行自己的练习可能造成占用，可先停止原练习窗口再重试。
5. 若换成其他空闲端口，要同步修改对应位置：目标服务端口改动时修改 -L 最后一段；客户端监听端口改动时修改 -L 前段和浏览器 URL。

`connect failed: Connection refused` 等提示可能意味着 SSH 已连通，但服务端到目标服务的连接失败。仅有转发监听成功不能证明目标网页可访问。

## 会话无响应时怎样退出

先区分是在等待密码、正在运行前台命令，还是网络已断开。前台命令通常可用 `Control + C` 中止；仍能输入命令时可以用 `exit` 退出 Shell。

如果交互式 OpenSSH 会话因断网卡住，且使用默认转义设置，可以依次按 **回车、`~`、`.`** 强制关闭该连接。它不是一条 Shell 命令，不需要粘成 `ssh ...` 执行；必须在新行开始输入，其他客户端或被修改的转义设置可能不同。

重新连接会建立新会话，不会自动恢复之前的终端位置或保证任务已完成。任务处理见[第六篇](06-security-and-operations.md#断开-ssh-不等于任务一定继续运行)。

## 多网卡时 B 一侧能连 另一侧不能连

沿用[第五篇的双网卡拓扑](05-network-and-tunnels.md#多网卡设备-b-应该怎样配置)：A 为 `192.168.10.10`；B 两侧分别为 `192.168.10.1` 和 `192.168.20.1`；C 为 `192.168.20.30`；两个网段掩码均为 `/24`。所有地址仍是虚构示例。

假设 A 能登录 B，C 却连不上 B，先按下面的顺序排查，不需要先开启 B 的系统 IP 转发。

1. **确认 C 连的是 B 的哪一个地址。** 本例在 C 使用 `ssh buser@192.168.20.1`，不要误连 C 自己，也不要在没有跨网段路径时用 B 的另一侧地址。
2. **确认 B 的网卡2确实持有该 IP，接口已启用。** 检查实际掩码和连接网络，不能只凭网线已插好或地址末尾是 `.1` 判断。
3. **确认 B 在网卡2的地址接收 SSH。** 只监听 `127.0.0.1` 或只监听 `192.168.10.1`，都不能证明 `192.168.20.1:22` 已开放。
4. **检查对应接口和来源的访问策略。** 两侧防火墙可能不同。若已经到达认证阶段，检查账号访问范围、`AllowUsers` 或 `Match` 等，而不是继续只查网线。
5. **检查 B 返回 C 的路径。** 多条默认路由、VPN、策略路由和过滤都可能影响返回路径；入站能到不等于回包一定正常。

### B 是 Linux 时的只读检查示例

以下命令只适用于安装了相应 iproute2 工具的 Linux，运行位置是 **B**。不要直接套用到 Mac 终端或 Windows PowerShell。Mac 可先从系统网络设置与“远程登录”入口核对地址和访问账号。

```bash
ss -lnt
```

查看 TCP 监听列表中的 22 端口：

| 监听地址示例 | 怎么理解 |
| --- | --- |
| `127.0.0.1:22` | 只在本机 IPv4 回环地址监听 |
| `192.168.10.1:22` | 这个条目只覆盖 B 的网卡1地址，需检查是否另有网卡2监听 |
| `0.0.0.0:22` | IPv4 通配监听，通常覆盖本网络环境中的各本地 IPv4 地址；仍需检查防火墙 |
| `[::]:22` | IPv6 通配监听；不能仅凭它就认定 IPv4 一定也能连接 |

表中是假设输出，不是已经观察到的设备状态。监听也可能由系统服务管理器提供；配置文件和实际列表不符时，还要检查启动配置是否生效。

如果 B 的源 IP 是 `192.168.20.1`，可查它发往 C 时的内核选路：

```bash
ip route get 192.168.20.30 from 192.168.20.1
```

关注出口 `dev`、下一跳 `via`（直连路由可能没有该字段）及相关源地址是否符合实际拓扑。这只是路由查询，不会替你添加路由，也不证明 C 的 SSH 端口可达。发现不符后先记录实际配置，再决定处理方式。[来源：ss 手册](https://man7.org/linux/man-pages/man8/ss.8.html)、[ip-route 手册](https://man7.org/linux/man-pages/man8/ip-route.8.html)

## A 能登录 B 但经 B 登录 C 失败

在 A 的终端查看完整跳板过程；先替换示例账号和地址：

```bash
ssh -vvv -J buser@192.168.10.1 cuser@192.168.20.30
```

按阶段判断：

| 失败位置或信息 | 下一步检查 |
| --- | --- |
| 到 B 的连接或认证失败 | 先修复 A 到 B 的地址、服务、主机身份或 buser 认证 |
| 通过 B 打开转发通道时提示 `administratively prohibited` | B 的 `AllowTcpForwarding`、`DisableForwarding`、`PermitOpen`、Match 或授权公钥限制 |
| 转发到 C 超时、被拒绝或报告不可达 | 从 B 看 C 的实际地址、端口、网络路径及 C 的服务/防火墙；具体提示不一定只有一个原因 |
| 已开始与 C 协商，主机身份检查失败 | 独立核对 C 的主机指纹，不要把 B 的指纹当成 C 的指纹 |
| C 返回用户认证失败 | 检查 A 的客户端用于 cuser 的认证材料，及 C 上的授权；不要误改成 B 的账号 |

“在 B 的 Shell 里手动 ssh 到 C 成功”也不等于跳板一定可用：手动连接可能使用 B 上的认证材料，而 `-J` 的目标认证由 A 完成，B 的转发策略也可能单独禁止该通道。

仅把 B 用作跳板，不要求它在面向 C 的网卡上监听 SSH。这里要检查的是 **B 能主动连接 C**，而不是不断增加 B 的 `ListenAddress`。详细条件见[第五篇跳板示例](05-network-and-tunnels.md#a-通过-b-登录-c)。

## 打开详细日志

在发起连接的本机终端执行：

```bash
ssh -vvv ssh-lab
```

详细程度随 `-v` 数量增加，最多三个。先从日志中确认四件事：

1. 实际连接的是哪个地址和端口。
2. 是否已经建立 TCP 连接。
3. 客户端尝试的是哪个账号、哪些认证方法和身份文件。
4. 是否出现认证成功，随后才发生其他错误。

日志可能包含账号、地址、目录、主机指纹和环境信息。分享前遮盖不愿公开的部分；不需要提供私钥或密码。

## 检查自己到底用了什么配置

```bash
ssh -G ssh-lab
```

核对 `hostname`、`user`、`port`、`identityfile` 和 `identitiesonly`。如果原以为登录远程，却配置到了 `127.0.0.1`，先改正配置。

## 只测试公钥认证

先完成第三篇的密钥生成和授权，再在本机 Mac 执行：

```bash
ssh -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -i ~/.ssh/id_ed25519_ssh_learning "$(whoami)"@127.0.0.1
```

这次测试不回退到账号密码。输入私钥口令不算回退密码认证。若使用了额外客户端配置，仍应通过日志确认实际提供的身份。

## 发现主机身份改变怎么办

先通过目标设备本地终端、可信管理员或控制台，查到新指纹并确认变化原因。[第二篇](02-first-connection.md)有本机查看主机公钥指纹的方法。

**只有完成独立核验以后**，才处理对应旧记录。例如已确认自连接练习的主机密钥变化，可以在本机运行：

```bash
ssh-keygen -R 127.0.0.1
```

如果是非默认端口，主机记录常用 `[地址]:端口` 表示，例如：

```bash
ssh-keygen -R '[127.0.0.1]:2222'
```

这些命令会修改主机记录，不是只读查询。替换或删除记录后，重新连接仍需核对新指纹。域名和 IP 可能有各自记录，要对应实际连接方式处理，不要清空整个文件。

## Mac 密钥权限检查

在本机 Mac 终端查看：

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/id_ed25519_ssh_learning ~/.ssh/id_ed25519_ssh_learning.pub ~/.ssh/authorized_keys
```

只对本教程的对应文件修正权限：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519_ssh_learning
chmod 600 ~/.ssh/authorized_keys
```

如果目标是另一台机器，目标 `authorized_keys` 的检查应在目标账号下做，修本机同名文件不会替目标授权。Windows ACL 与 Mac/Linux 权限模型不同，不要在 PowerShell 中直接套用这些 `chmod` 命令。

## 几个一眼能查的命令

| 目的 | 命令 | 执行位置 |
| --- | --- | --- |
| 看客户端版本 | `ssh -V` | 本机终端或 PowerShell |
| 看当前账号 | `whoami` | 当前系统，注意是否已登录远程 |
| 看主机名 | `hostname` | 当前系统 |
| 发起别名连接 | `ssh ssh-lab` | 配置别名的客户端 |
| 看配置，不登录 | `ssh -G ssh-lab` | 客户端 |
| 看详细连接日志 | `ssh -vvv ssh-lab` | 客户端 |
| 看代理中身份的指纹 | `ssh-add -l` | 客户端，需代理可连接 |
| 看用户公钥指纹 | `ssh-keygen -lf ~/.ssh/id_ed25519_ssh_learning.pub` | 存放该公钥的 Mac 终端 |
| 退出当前远程 Shell | `exit` | 已登录的远程 Shell |

## 提问时记录这五项

1. 哪台机器连接哪台机器，分别是什么系统。
2. 同一局域网、跨家庭网络，还是云服务器。
3. 执行的命令，隐藏敏感地址但保留参数结构。
4. 完整报错，以及是否曾经成功。
5. 最近改过什么，例如密码、密钥、IP、系统、网络或配置。

示例：“Windows PowerShell 连接同一家庭网络的 Mac。Mac 自连接成功，Windows 连接 Mac 局域网 IP 超时，最近换过路由器。”这比只说“SSH 用不了”更容易定位。
