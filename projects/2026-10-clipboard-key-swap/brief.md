## 背景

- 为什么要做这个项目：2026-10-17 复制一类 API Key 时，粘贴出来的不是刚复制的那串。用户用 WorkBuddy + Deepseek-V4.1-Flash 把这件事查到了注入进程和安装来源，值得写成可复用的排查故事。
- 触发来源：用户要求基于默认分支开新分支，先完整保存对话 https://workbuddy.link/p/C3fFCucq59deI8f8qR3Pax ，再做成文章和视频。
- 期望解决的问题：让读者知道这种「复制被换掉」不是手滑，也给出发现后该先做什么、不该做什么。

## 目标

- 内容目标：一条叙事，四段链路：发现、排查、溯源、修复。
- 业务目标：作为 WorkBuddy 实战案例，展示它能陪着做本机对照实验，而不是只给一份清单。
- 学习或沉淀目标：留下这次对话原文，方便以后改稿时核对，不靠记忆复述。

## 受众

- 核心读者/观众：经常复制 API Key、Token 的开发者。
- 已有认知：知道剪贴板、Win+V、计划任务大概是什么。
- 主要痛点：复制一次却多出一条几乎一样的密钥，分不清是软件同步还是被人换了。
- 可能误解：以为是 WorkBuddy、飞书或 VS Code 的复制按钮有 bug；或者以为删掉某个 exe 就干净了。

## 内容边界

- 必须覆盖：现象、对照实验、排除过程、锁定 `UserAccountBroker.exe` 内存注入、2026-04-20 第三方安装包与伪装计划任务、止血顺序和边界。
- 暂不覆盖：样本的逆向细节、可直接执行的注入/对抗步骤、其他机器是否中招。
- 不能说或需要谨慎表达：不贴完整密钥；不把对话里的清理建议写成「已经修复」；不承诺 Defender 一定能扫到反射注入；不点名教人如何绕过扫描。
